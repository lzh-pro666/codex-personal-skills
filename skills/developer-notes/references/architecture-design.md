# 需求架构设计模板

仅用于 `note_type: architecture-design`。保持方案可决策、可实施、可验收；删除无内容或无价值的章节。

```markdown
---
title: <需求或能力 + 架构设计>
tags:
  - architecture
note_type: architecture-design
status: proposed
created: YYYY-MM-DD
updated: YYYY-MM-DD
---

# <需求或能力 + 架构设计>

> [!summary]
> 用 1–2 句话说明目标、核心方案和关键取舍。

## 背景与目标

为什么要做、要解决什么问题、成功标准是什么。

## 范围

- 包含：
- 不包含：

## 现状与约束

现有链路、依赖、兼容性、性能、交付或历史约束。

## 方案设计

### 整体方案

核心设计及其工作方式。涉及三个以上组件、跨层依赖或关键交互时，必须按质量规则补充架构、数据流或时序图；简单链路不要添加装饰性图表。

### 模块职责

只列发生变化或新增的模块及边界。

### 数据流与接口

记录关键调用链、状态变化、接口或数据模型变化。

### 失败路径与降级

记录关键失败如何传播、用户可见行为、重试或降级方式，以及恢复或回滚边界。没有材料失败路径时删除本节。

### 兼容与迁移

仅在涉及旧版本、历史数据、灰度或回滚时保留。

## 方案对比与取舍

记录真正考虑过的备选方案、选择理由和代价，不罗列虚构方案。

## 风险与对策

只记录具体风险、触发条件和缓解措施。

## 实施计划

按可交付阶段列出关键改动、依赖和顺序。

## 验收与测试

功能、代码质量、边界、兼容、性能、失败路径及必要的监控标准。区分计划中的标准与已执行的验证证据。

## 追踪关系

| 需求 / 验收项 | 设计 | 实现 | 测试 / 验证 |
| --- | --- | --- | --- |
| 具体需求 ID 或验收项 | 本文的方案章节或决策 | 文件、符号或“未实现” | 测试、命令、人工证据或“待验证” |

只在存在具体项目需求、规格或实现来源时保留。每个实质性需求至少对应一行，使用精确的 ID、标题、文件、符号、测试、现有报告或已观察的命令结果。只读到测试源码时，记录它拟覆盖的行为，不得声称已通过；没有执行证据时填“待验证”。整理本笔记本身不授权重新运行测试或其他项目命令。

## 决策与待办

- 已确认：
- 待确认：

## 关联

- [[已存在的相关笔记]]

## 参考

- [外部一手资料](https://example.com)
```

标题要包含需求或能力名称，避免只写“架构设计”。生命周期只使用 `proposed → accepted → implemented → superseded`，且必须由证据驱动。尚未实现的方案保留“未实现 / 待验证”追踪状态，不因表格完整或质量评分而提前提升文档状态。仅在值已知时添加 `aliases`、`project`、`source_refs` 等可选属性。
