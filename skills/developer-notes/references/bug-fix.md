# Bug 修复模板

仅用于 `note_type: bug-fix`。突出可复现证据、根因、最小修复和回归验证；不要把猜测写成结论。

```markdown
---
title: <技术或模块 + 症状或修复结果>
tags:
  - debugging
note_type: bug-fix
status: investigating
created: YYYY-MM-DD
updated: YYYY-MM-DD
---

# <技术或模块 + 症状或修复结果>

> [!summary]
> 用 1–2 句话说明症状、当前根因结论以及排查或修复状态；未知项明确写“尚未确认”。

## 影响与环境

影响用户或范围，以及系统版本、设备、配置、触发条件等必要环境。

## 现象与复现

1. 最短复现步骤
2. 实际结果
3. 预期结果

保留关键错误文本、日志或堆栈；没有可靠复现步骤时明确说明。

## 排查证据

记录定位根因所需的关键观察。失败尝试仅在能排除重要方向时保留。

性能缺陷必须记录可复现的测量方法、修复前指标和修复后指标；无法测量时明确数据缺口，不要只写“已优化”。

## 根因

描述已确认的具体机制，并区分事实与推测；根因未确认时记录证据支持的假设，不强行下结论。

## 修复方案

仅在已有修复时保留。说明最小有效修复、为什么生效，以及未采用其他方案的必要理由。

## 代码与配置变更

仅保留关键 diff、代码、命令或配置，避免粘贴无关文件。

## 验证与回归

- 原问题验证：
- 边界场景：
- 回归范围：
- 自动化测试或监控：

涉及异步时序、生命周期、状态机或多分支根因时，补充能解释机制的 Mermaid 图；线性且简单的 Bug 不要为了形式添加图。

## 风险与预防

仅在存在副作用、回滚条件或可复用预防措施时保留。

## 关联

- [[已存在的相关笔记]]

## 参考

- [Issue、PR 或一手资料](https://example.com)
```

写入时根据证据选择状态，生命周期只使用 `investigating → fixed → monitoring`。仅在值已知时添加 `aliases`、`severity`、`project`、`source_refs`。如果修复包含架构影响，在“修复方案”中增加子节说明；不要因此再创建内容重复的架构笔记。
